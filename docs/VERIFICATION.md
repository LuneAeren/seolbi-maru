## 자동 테스트 범위

1. 데모 초기화, CSP, 16개 샘플 설비와 비활성 연결부 표시.
2. CSRF·다른 출처 쓰기 거절, 임의 사용자 헤더로 데모 신원 변경 불가.
3. 불완전한 운영 설정 시작 거절, 유효한 서명 없는 운영 인증 거절, 운영 샘플 자동 생성 없음.
4. 버전 충돌, 이력, 삭제 상태와 이전 버전 복구.
5. CSV의 한글·따옴표·쉼표·줄바꿈·앞자리 0 보존, 잘못된 파일·중복 열·경로형 파일명 거절.
6. XLSX 시트 처리, 문자열 출력, 수식을 실행하지 않는 텍스트 반입.
7. 외부 관계 링크가 있는 XLSX와 올바르지 않은 압축 형식 거절.
8. 파일 반입·열 이름 매핑·셀 수정·미저장 출력·공유본 유지·충돌·원본 바이트 보존.
9. CSV 수식 방어와 업무사이트 허용 목록.
10. SQLite 재시작 후 자료 보존, 같은 버전으로 20개 동시 저장 시 정확히 1개 성공·19개 충돌.
11. 2MiB를 넘는 가짜 CSV에서 18,000행 파싱과 앞자리 0 보존.
12. 내부 스냅샷 검증 실패 시 정상본 유지 및 정상 전체 스냅샷의 원자적 교체.

- 업무자료 표를 열고 셀을 수정한 뒤 닫을 때 미저장 확인 표시.

- XLSX 파일 업로드, 2개 시트 미리보기와 두 번째 시트 선택.
- 선택한 시트의 자료 등록 및 `001` 문자열 보존 확인.

- 최종 대시보드 재로딩과 로컬 자산 경로(`/mark.svg`, `/styles.css`, `/app.js`) 확인.

## 의존성 검토

- 직접 의존성: express 5.3.0, helmet 8.3.0, csv-parse 7.0.3, exceljs 4.4.0, yauzl 3.4.0. 전체 잠금 파일과 DEPENDENCIES.json을 제공한다.
- 최초 검사에서 ExcelJS의 uuid 의존성에 알려진 취약점이 발견되어 uuid 11.1.1로 override했다. XLSX 반입·출력 테스트 후 알려진 취약점 0개를 확인했다.
- ExcelJS에는 fstream·rimraf·glob·inflight·lodash.isequal 등 유지보수 중단 경고가 있는 전이 의존성이 남아 있다. 알려진 취약점 0개와 유지보수 상태는 다른 기준이며, 회사 반입 검토에서 패키지 목록을 함께 확인해야 한다.
- 설치 스크립트는 실행하지 않았다. 의존성 원문 전체를 사람이 감사하거나 별도 악성코드 엔진으로 검사하지 않았다.

## 아직 검증하지 않은 항목

- 실제 회사 SSO, 인증 프록시·서명 전달, 부서 사용자 식별.
- 실제 Hue·Splunk 조회·보안 차단 원인·스케줄러.
- Windows·Microsoft Edge·사내 서버·HTTPS·방화벽 환경.
- 브라우저 및 서버의 패킷·DNS를 포함한 외부 송신 차단 실측. 확인한 것은 자체 런타임 소스 정책·CSP·로컬 DOM 자산 경로다.
- 20명 장시간 사용 시 응답·메모리·디스크 부하와 운영 백업·복구.
- 모든 변종 악성 파일, 모든 ZIP/XML 파서 취약점, OS 수준의 격리.

이 결과는 가짜 데이터 기반 첫 구현의 검수 결과이며 사내 운영 승인이나 악성코드 부재·무유출의 절대적 보증이 아니다.

디자인 대상은 회사 업무 포털의 홈화면이다. 새 `/home-designs/`에 설비현황·업무자료·업무사이트 중심의 16개 별도 구성을 작성했다. 이전 일정 화면 16안은 보존하고 링크·README·AI 지침에서 구분했다.

- 홈 16개 HTML의 렌더링, 제목·구성, 각 대표 조작 1개씩을 브라우저에서 확인했다. 전부 통과한 기록은 HOME-BROWSER-CHECKS.json에 있다.
- 홈의 설비 선택, 사이트 분류, 상태 필터, 브리핑 펼치기, 자료 종류 필터, 좌우 패널 전환, 모듈 숨기기, 담당자 필터, 단계별 진입, 구역 전환, 통합 검색, 목적별 탭, 디렉터리 펼치기, 활동 유형 필터, 확인 표시, 4분할 표 필터를 확인했다.
- 캘린더에서 가짜 업무를 매 3일, 11월 16~22일로 저장했다. 16·19·22일 총 3건이 생성되어 주간 화면에 나타났다.
- 같은 기간 미리보기는 새 업무 0·기존 3, 재생성은 추가 0·중복 3으로 표시됐다. 중지 시 발생일 0, 재개 후 기존 업무는 보존됐다.
- 19일 업무를 선택해 장소와 상세의 반입값을 확인한 뒤 장소·상세를 수정하고 일정을 지정했다. 선택 작업 화면에서 변경값을 확인했다.
- 개별 일정·장소를 바꾼 후에도 원래 반복 발생일이 중복 생성되지 않도록 매크로 ID+발생일을 고정했다. 관련 자동 테스트에 이동·수정 후 중복 방지를 포함했다.
- 새 5개 자동 테스트: 장소·상세 보존/길이/오류 시 무변경, N일 간격·메타데이터·재생성 중복, 중지/재개와 실패 시 원본 유지, 간격/기간/윤년 경계, CSRF/버전과 홈 16개 경로·고유 UX·CSP.
- JavaScript 31개 파일의 문법·제한된 소스 정책 검사를 통과했다. 추가 패키지·외부 런타임 요청은 없다.

화면 증거는 전달 폴더의 home-design-01.jpg~16.jpg, home-design-gallery-16.jpg, calendar-recurring-v0.4.jpg다. 생성한 업무와 매크로가 들어 있는 실행 DB는 GitHub·ZIP에 포함하지 않는다. 반복 생성은 지정한 기간을 미리 만드는 기능이며 백그라운드 생성 스케줄러는 포함하지 않는다. 실제 회사 계정·메일·DB·Windows·Edge 검증은 사내에서 진행해야 한다.
