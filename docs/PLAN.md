# 설비마루 개발계획 v1.0

작성일: 2026-11-14 (한국 시간)
상태: 요구사항 수집 완료, 구현 전 검토본. Splunk 사용과 기존 사내 계정 로그인이 확인되었다. 확인된 요구사항과 구현 제안을 구분한다. 구체적인 사내 연결 방식은 사내 에이전트가 확인한다. 현재 단계는 계획 문서 정리와 GitHub 인계다. 앱 소스 구현, 설치, 서버 설정 변경, 배포는 수행하지 않았다.

## 1. 목표와 확인된 요구사항

- Windows와 Edge를 사용하는 부서원 약 20명이 사내 웹서버에서 공동 사용한다.
- 핵심 메뉴는 오늘 업무 한눈에 보기, 업무자료, 업무사이트다.
- 요약은 카드로, 여러 건의 상세 데이터는 표로 보여준다.
- 자료는 사내 서버에 보관하며 주로 CSV를 사용한다. 원본이 Excel 또는 PDF인 경우도 있다.
- 기존 개발 환경은 Streamlit과 Express.js다. 각각의 현재 역할과 사용 버전은 미확인이다.
- 주요 데이터 출처는 Hue와 Splunk다.
- 현재 포털은 사내 계정으로 로그인한다. 새 외부 인증 서비스를 추가하지 않고 기존 사내 인증을 활용하는 방향으로 설계한다.
- 오늘 업무에는 설비현황과 설비에 관한 인폼을 표시해야 한다.
- 부서원 모두 자료와 업무 내용을 편집할 수 있어야 한다.
- CSV·Excel 표를 가져와 수정하고 새 파일로 내려받아야 한다.
- 보통 파일 하나가 약 2MB이며 텍스트 위주다. 행·열 수와 동시 작업량은 아직 모른다.
- 기존에는 DB 및 사내 자료 연동을 사용하지만 일부 데이터 누락과 수동 업로드가 발생한다.
- 외부에서는 가짜 데이터로 범용 뼈대를 개발한다. 사용자의 GitHub를 거쳐 사내 에이전트가 코드를 반입하고 내부 연동을 완성한다.
- 운영 중 업무자료가 외부로 전송되지 않아야 하며 악성 동작과 취약점 검증이 중요하다.

## 2. 개발 및 운영 경계

| 위치 | 처리할 것 | 포함하지 않을 것 |
| --- | --- | --- |
| 외부 개발 환경 및 GitHub | 범용 소스, 가짜 데이터, 가짜 설정 예시, 테스트, 설치·검수 설명 | 회사 업무자료, 내부 주소·경로, 사용자 명단, 인증정보, 실데이터가 담긴 로그·화면 |
| 사내 개발·검수 환경 | 내부 설정, 사내 로그인·DB 연결, 실제 자료 매핑, 회사 검사 도구로 검수 | 승인되지 않은 외부 분석·업로드·오류수집 서비스 |
| 사내 운영 서버 | 승인된 내부 시스템과 통신, 파일 보관, 공유 데이터 관리 | GitHub 자동 조회, 외부 CDN·폰트·분석도구·AI 호출·자동 업데이트 |

GitHub에서 코드를 가져오는 행위는 개발·반입 절차다. 운영 사이트가 GitHub에 접속할 필요는 없도록 구성한다. 사내 에이전트도 회사가 허용한 실행·통신 범위 안에서 사용하며, 회사 파일을 외부 모델로 전달할 수 있다고 가정하지 않는다.

프로젝트 이름은 설비마루(Seolbi Maru), 저장소 이름은 seolbi-maru로 정했다. 사용자의 GitHub 계정에 비공개 저장소로 계획 문서를 전달한다. 비공개 저장소에도 회사 자료와 인증정보를 넣지 않는다. 실제 설정·업로드 자료·백업·로그는 Git 추적 대상에서 분리하고 커밋 전 검사한다.

## 3. 화면 구성 초안

| 화면 | 주요 내용 | 동작 |
| --- | --- | --- |
| 오늘 업무 | 설비현황 요약 카드, 설비별 상태 표, 최근 설비 인폼, 관심 설비 | 상태 카드를 누르면 설비 표를 필터링한다. 설비를 고르면 해당 인폼·메모·자료·업무사이트를 함께 연다. 상태 분류와 지표 계산은 실제 업무에 맞게 사내에서 확정 |
| 업무자료 | 분류, 제목, 설명, 갱신 시각, 원본 파일, CSV·Excel 표 | 검색·정렬·필터·페이지 이동·표 편집·새 파일 다운로드. 원본은 보존 |
| 업무사이트 | 업무별 링크 카드, 설명, 즐겨찾기 | 부서원이 등록한 허용 목록 안의 사내 주소만 열기. 외부 아이콘·미리보기 자동 수집 없음 |
| 자료·링크 편집 | 자료 업로드, 열 매핑, 검증 결과,링크·설명 편집, 변경 이력 | 모든 부서원이 사용. 미리보기 후 반영, 충돌·실패 사유 표시, 이전 버전 복구 |

본문과 주요 조작은 16px 이상, 보조 텍스트는 14px 이상을 제안한다. 표에는 고정 헤더와 제한된 스크롤 영역을 두고, 열이 많으면 가로 스크롤과 열 선택으로 처리한다. 긴 상세는 별도 패널에 표시한다. 정확한 해상도는 미정이다.

## 4. 데이터 구조와 연동 방식

Streamlit과 Express.js를 활용하는 다음 구성을 제안한다. 기존 두 기술의 실제 배치와 책임은 미확인이므로, 사내 에이전트가 현행 구조를 확인한 뒤 기존 인증·저장 기능을 재사용한다.

| 구성 | 제안 역할 |
| --- | --- |
| 기존 사내 진입점·인증 계층 | Edge 접속, 사내 HTTPS, 사용자 식별과 부서 접근 제한 |
| Streamlit | 카드·설비 표·인폼·자료 편집 화면, 파일 미리보기·변환·다운로드 |
| Express.js | 공유 자료 API, 서버 측 권한 검사·입력 검증, 버전 확인·저장, 변경 이력, 승인된 내부 데이터 연결 |
| 포털 저장소 | 설비 인폼·메모, 자료 메타데이터와 버전, 편집 이력, 동기화 결과 저장. 기존 사내 저장소 재사용 우선 |
| 원본 파일 저장소 | 업로드 원본과 생성한 파일 보관. 포털 저장소에는 내부 식별자만 저장 |

기본 데이터 흐름은 Edge → Streamlit → 내부 Express API → 포털 저장소 또는 승인된 내부 조회 연결부다. 기존 사내 인증 계층에서 확인한 사용자 신원을 서버 사이 호출까지 전달하는 방식은 현행 인증 구현에 맞춰 사내에서 정한다. 브라우저가 임의로 보내는 사용자명·헤더를 신뢰하지 않는다.

Streamlit의 표 편집과 다운로드 위젯을 활용하는 구현을 제안한다. 편집 위젯만으로 공유 저장·동시 수정 문제가 해결되지는 않으므로 서버 저장과 버전 검사를 별도로 만든다. 실제 사내 사용 버전에서 API 지원 여부를 확인한다. [Streamlit 표 편집](https://docs.streamlit.io/develop/api-reference/data/st.data_editor), [Streamlit 다운로드](https://docs.streamlit.io/develop/api-reference/widgets/st.download_button)

Hue는 DB·데이터웨어하우스를 조회하는 SQL 도구다. Hue라는 이름만으로 실제 DB·연결 프로토콜·허용된 API를 확정할 수 없다. 사내 에이전트가 현행 승인 경로를 확인하고 기존 조회 결과 반입 또는 승인된 API·DB 경로를 사용한다. 브라우저 자동 조작이나 우회 수집은 구현하지 않는다. [Hue 공식 설명](https://docs.gethue.com/)

Splunk 연결부를 설계에 포함한다. 사내에서 허용하는 API·인증·검색 결과 제한·작업 완료 확인 방식은 사내 에이전트가 현행 연동을 조사해 정한다. Hue·Splunk 연결은 내부 설정을 넣고 명시적으로 활성화한 경우에만 동작하게 한다. 외부 개발의 기본 실행 경로는 가짜 데이터이며 실제 시스템 주소·자격증명은 포함하지 않는다.

화면은 일정한 데이터 형식만 사용하고, 데이터 공급 부분은 다음처럼 교체할 수 있게 나눈다.

- 가짜 데이터 공급: 외부에서 화면·상호작용과 오류 처리를 검증한다.
- CSV 공급: 사내 서버에서 파일 업로드와 변환 결과를 저장한다.
- 내부 시스템 공급: 사내 에이전트가 승인된 DB 또는 API에 연결한다.

세 공급 방식은 사내의 공통 저장·조회 계층을 통해 화면으로 전달한다. 브라우저에서 DB에 직접 접속하지 않는다. DB 조회에는 필요한 최소 권한을 사용하고, 원천 DB 쓰기는 기본 범위에 넣지 않는다.

공유 데이터와 변경 이력은 서버에 저장한다. 브라우저 저장소는 관심 설비·열 표시·정렬 등 개인 화면 설정에 한정한다. 모든 부서원은 포털 내용과 자료를 편집할 수 있다. 원천 시스템의 DB 쓰기 권한까지 부여한다는 의미는 아니다.

공동 편집은 다음 방식으로 구성한다.

- 편집 시작 시 자료 버전을 함께 읽고 저장 시 서버에서 버전을 원자적으로 비교한다.
- A와 B가 같은 버전을 열고 A가 먼저 저장하면, B의 저장은 충돌로 처리하고 최신 내용과 자신의 수정 내용을 확인하게 한다. 자동 덮어쓰기는 하지 않는다.
- 화면에서 셀을 바꾼 상태, 새 파일 다운로드, 부서 공유본 저장을 구분한다. 공유본 저장은 명시적인 저장 동작으로 실행한다.
- 작성자·저장 시각·대상·버전·변경 사유를 기록한다. 상세 변경 내용이 필요하면 접근 통제되는 사내 이력 저장소에만 보관한다. 일반 오류 로그에 자료 원문을 복사하지 않는다.
- 삭제는 복구 가능한 상태 변경을 기본으로 한다. 운영 설정·인증정보·연결 허용 목록 변경은 콘텐츠 편집과 분리해 운영자가 관리하는 것을 제안한다.
- 기존 사내 계정 로그인에서 확인된 사용자 식별자를 편집자·버전 충돌·권한 검사에 사용한다. 이 신원이 Streamlit에서 Express까지 신뢰할 수 있게 전달되는지 사내에서 검증한다. 임의 사용자명·브라우저 입력 헤더를 인증으로 사용하지 않는다. 가짜 로그인은 외부 샘플에서만 허용하며 운영 설정에서는 인증 확인에 실패하면 접근을 거절한다.

각 자료에는 출처, 원천 식별자, 반입 시각, 데이터 기준 시각, 버전, 변경 사유를 남기는 것을 제안한다. 실제 필드명과 업무 규칙은 사내에서 채운다.

### 설비현황과 인폼의 초기 데이터 형식

아래는 회사 실데이터가 아닌 뼈대 개발용 제안이다. 명칭과 열 매핑은 사내에서 변경할 수 있게 한다.

| 자료 | 초기 제안 필드 |
| --- | --- |
| 설비현황 | 내부 설비 키, 표시명, 구역·분류, 원천 상태 코드, 표시 상태, 상태 기준 시각, 출처 |
| 설비 인폼 | 인폼 키, 연결 설비 키 또는 공통 범위, 제목, 본문, 게시·적용 시각, 유효 기간, 작성자, 버전 |
| 작업 메모 | 메모 키, 연결 설비 키, 내용, 처리 상태, 작성자, 작성·수정 시각, 버전 |
| 자료 | 자료 키, 연결 설비·분류, 제목, 내부 원본 파일 키, 열 매핑, 현재 버전 |
| 업무사이트 | 링크 키, 이름, 설명, 분류·연결 설비, 허용된 내부 주소 |

설비 상태 분류는 설정으로 둔다. 운전·정지·점검 등은 샘플 상태이며 회사의 실제 분류라고 표시하지 않는다. 상태를 가져오지 못한 설비는 확인 불가로 구분하며, 데이터가 없다는 이유로 정상으로 집계하지 않는다. 설비의 중복 기준·최신 상태 선택 규칙·집계 기준 시각을 사내 매핑에 명시한다.

인폼의 게시 시각과 실제 적용 시각을 구분하고 오래된 인폼이 계속 상단에 남지 않도록 유효 기간·보관 처리를 제공한다. 사용자 PC와 서버 시간대가 다를 수 있으므로 표시 기준 시간대를 설정으로 두고 초기 화면에 기준을 표시한다.

### 일부만 들어오는 문제

현재 정보로는 보안 차단, 권한, 쿼리, 페이지 처리, 시간초과, 원본 변경 중 어느 것이 원인인지 판단할 수 없다. AI 사용 증가가 원인이라고 단정하지 않는다. 사내에서 연결별 실행 결과와 오류를 확인한다.

- 연결마다 마지막 시도 시각, 마지막 정상 반영 시각, 읽은 건수, 거절한 건수, 반영한 건수를 구분한다.
- 성공·실패·일부 거절·기준 시각 경과 상태를 구분한다. 지연 판정 시간은 업무별로 정한다.
- 원천의 전체 건수를 확인할 수 없는 경우 완전 수집이라고 표시하지 않는다.
- 조회 실패를 0건 또는 정상 처리로 바꾸어 표시하지 않는다.
- 새 데이터 전체 검증이 끝난 뒤 교체한다. 실패하면 직전 정상 버전과 갱신 실패 상태를 표시한다.
- 이전 데이터도 사용할 수 없는 업무는 오래된 수치를 보여주는 대신 확인 불가로 표시한다. 적용 업무는 담당자가 정한다.
- 자동 반영 자료의 수동 보정은 원본과 분리하고, 다음 동기화에서의 유지·취소 규칙을 정한다.

## 5. CSV·Excel·PDF 편집

확정된 첫 버전 요구는 CSV·Excel 표를 가져와 편집하고 새 CSV 또는 XLSX로 내려받는 것이다. 업로드한 원본은 보존한다. 새 XLSX는 편집한 표 데이터로 생성하며 원본 통합문서의 모든 서식·차트·수식·매크로를 그대로 보존하는 편집기는 범위에 넣지 않는다.

평균 약 2MB 텍스트 파일을 기준으로 가짜 검수 파일을 만든다. 파일 크기만으로 최대 행·열 수와 20명 동시 사용 성능을 단정하지 않는다. 첫 버전에서 파싱 크기·행·열 수·셀 길이·처리 시간을 제한하고, 파일 형식별 상한은 실제 가짜 파일 검수 후 설정한다. Excel 압축 해제 후 크기와 셀 수 제한도 포함한다. 큰 표는 조회 범위를 제한하고 편집 단위별로 나누며, 필터링된 일부만 보이는 상태에서 전체 자료를 덮어쓰지 않도록 한다.

CSV 반입은 다음 순서로 구성한다.

1. 허용된 사용자가 파일을 올린다.
2. 인코딩과 구분자를 확인하고 미리보기를 제공한다. UTF-8과 한국어 Windows 환경의 인코딩 차이를 검증 사례에 포함한다.
3. 원본 열과 업무 필드를 연결한다.
4. 필수값, 자료형, 중복 키, 날짜, 행·열 수와 파일 크기를 검사한다.
5. 반영·거절 예정 건수와 오류 위치를 확인한다.
6. 전체 검증 후 새 버전을 반영하고 직전 버전으로 복구할 수 있게 한다.

CSV의 따옴표, 쉼표, 줄바꿈, 한글을 처리하는 검증 사례를 둔다. 화면에는 셀 내용을 문자로 표시하며 HTML·스크립트로 실행하지 않는다. CSV를 다시 내보낼 때에는 스프레드시트에서 수식으로 해석될 수 있는 입력에 대한 처리를 정하고 검증한다.

첫 버전 Excel 형식은 XLSX를 제안하며, 시트를 선택해 표로 반입한다. 구형 XLS·매크로 파일·암호화 파일은 자동 지원하지 않고 필요한 경우 지원 범위를 추가한다. 사내 서버에서 파싱하고 수식·매크로·외부 링크를 실행하거나 갱신하지 않는다. 수식 셀이 있으면 탐지해 표시하고, 텍스트로 반입하거나 저장된 계산값 사용을 명시적으로 선택하게 한다. 저장된 계산값이 없거나 최신 여부가 불확실하면 이를 표시한다.

표 편집에서는 설비 ID·품번 등 앞자리 0이 필요한 값을 문자열로 보존하고, 열별 자료형을 지정한다. 새 XLSX의 문자열은 수식으로 해석되지 않게 출력하고, CSV 수식 방어 처리로 값이 달라지는 경우 다운로드 전에 안내한다. 생성한 파일을 다시 읽어 수정값·한글·날짜·빈값·앞자리 0 보존을 검사한다.

PDF 직접 표 추출·편집은 첫 버전 필수로 확인되지 않았으므로 별도 범위로 둔다. 사내에서 허용한 원본 자료 등록·다운로드는 유지하고, 자동 추출이 필요해지면 텍스트형·스캔형 구분과 사람의 확인 단계를 추가한다. 외부 OCR·AI 서비스로 보내지 않는다.

파일은 확장자만 신뢰하지 않고 허용 형식, 내용, 크기, 파일명·경로, 권한을 함께 검증한다. 저장 파일이 코드로 실행되지 않도록 웹 실행 경로와 분리하고, 회사에서 제공하는 사내 검사 도구를 연결한다. 외부 파일 검사 사이트에 업로드하지 않는다. [OWASP 파일 업로드 지침](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## 6. 외부 전송 및 악성 동작 검증 기준

### 구현 기준

- 운영에 필요한 스크립트·스타일·아이콘 등은 내부에서 제공한다. 외부 CDN, 웹폰트, 분석, 원격 오류 수집, 자동 업데이트 의존성을 두지 않는다.
- 외부 URL의 아이콘·문서 미리보기·링크 내용을 자동으로 불러오지 않는다.
- 업로드 자료의 HTML·스크립트 실행, 동적 코드 평가, 임의 명령 실행 기능을 만들지 않는다.
- 업무사이트 링크에는 사내에서 설정하는 명시적 허용 목록을 적용한다. 임의 URL을 서버가 대신 가져오는 기능은 두지 않는다.
- 서버의 모든 조회·수정·업로드·다운로드에서 권한을 검사한다. 화면에서 버튼을 숨기는 것만으로 권한을 구현하지 않는다.
- 원문 자료, 인증정보, 전체 쿼리 결과를 오류 로그에 남기지 않는다.
- 의존성은 필요한 범위로 줄이고 버전, 라이선스, 출처, 설치 스크립트, 알려진 취약점과 실제 포함 파일을 검토한다. 자동 검사의 통과만으로 악성코드 부재를 단정하지 않는다.

### Streamlit·Express 환경에서 추가할 기준

- Streamlit 사용 통계 전송을 끈다. 공식 설정의 browser.gatherUsageStats는 현재 문서상 기본값이 true다. 사내 버전과 환경변수·실행 인자까지 포함한 최종 적용값을 확인하고 브라우저와 서버에서 검증한다.
- CORS·XSRF 보호를 끄는 방식으로 배포 문제를 해결하지 않는다. 승인된 출처·호스트와 프록시 경로를 맞춘다.
- 테마·폰트·아이콘과 컴포넌트 자산을 로컬 제공하고, 원격 테마·웹폰트·원격 스크립트를 사용하지 않는다. 필요 없는 원격 에이전트 API·사용자 정의 컴포넌트는 활성화하지 않는다.
- Streamlit의 내부 WebSocket 연결은 허용하되 승인되지 않은 목적지는 차단하도록 실제 동작에 맞춰 CSP와 프록시를 검수한다. 전체 스크립트 출처를 무제한으로 여는 예외는 두지 않는다.
- Express에는 서버 입력 검증, 사내 인증·권한, 보안 헤더, 요청·파일·처리 시간 제한, 비밀값 보호를 적용한다. 인증·헤더 정책은 실제 Streamlit 연결과 함께 검증한다.

이 항목은 현재 공식 문서를 근거로 한 구현 제안이다. 사내에 설치된 버전을 확인하기 전에는 같은 옵션이 모두 지원된다고 가정하지 않는다. [Streamlit 설정](https://docs.streamlit.io/develop/api-reference/configuration/config.toml), [Express 보안 지침](https://expressjs.com/en/advanced/best-practice-security/)

### 통신 통제

CSP는 페이지가 불러올 리소스 출처를 제한하며, connect-src는 fetch·WebSocket·sendBeacon 등의 연결을 제한한다. 이미지·스크립트·스타일·프레임·폼 등에도 각각 적절한 정책을 적용할 계획이다. 외부 보고 수집 주소도 두지 않는다. [MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy), [MDN connect-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src)

CSP만으로 브라우저의 모든 이동, 서버의 통신, 운영체제·확장프로그램까지 통제할 수 있다고 보장하지 않는다. 사내 보안 담당자에게 운영 서버의 외부 송신 차단과 클라이언트의 허용된 통신 경로를 확인받고, 애플리케이션 통제와 함께 검수한다. 방화벽 등 회사 설정은 이 개발 작업에서 임의로 바꾸지 않는다.

### 확인 가능한 합격 조건

- 실제 배포할 파일과 소스의 대응을 기록하고, 파일 목록·해시·의존성 목록을 전달한다.
- 외부 연결이 차단된 사내 검수 환경에서 모든 필수 화면과 자료 처리를 실행한다.
- 초기 로딩뿐 아니라 검색, 업로드, 편집, 다운로드, 오류 처리, 갱신까지 브라우저 요청과 서버 통신 기록을 확인한다.
- 허용 목록 밖 요청 시도도 실패로 기록한다. 차단되어 자료가 전달되지 않았다는 이유만으로 정상 합격시키지 않는다.
- 스크립트처럼 보이는 셀, 부적절한 링크, 잘못된 파일명·경로, 권한 없는 수정, 위조된 파일·대용량 입력을 처리하는지 검증한다.
- 실제 파일 업로드와 파싱 후 결과를 회사 검사 도구로 확인하고, 사내 테스트 서버에서 검수 후 운영 반영한다.
- 검수 범위, 도구·버전, 검사 결과, 남은 제한을 기록한다. 악성코드가 절대 없다는 보증으로 표현하지 않는다.

## 8. 구현 작업 순서와 검증

1. 가짜 설비·인폼·자료·링크와 고정된 데이터 형식을 만든다. 일부 수집 실패, 오래된 자료, 중복 키, 원천 상태 미확인 예시를 포함한다.
2. Streamlit에 오늘 업무, 업무자료, 업무사이트 화면을 구성한다. 카드·표·설비 상세·필터·빈 결과·실패 상태를 먼저 완성한다.
3. Express API와 공통 저장 계층에 공유 자료, 버전 비교 저장, 변경 이력, 원본 파일 보관을 구현한다. 원천 데이터의 연결부는 기본 비활성으로 둔다.
4. CSV·XLSX 업로드 → 검증·열 매핑 → 표 편집 → 새 파일 다운로드와 공유본 저장을 구현한다. 미저장 상태와 충돌 해결 화면을 포함한다.
5. 가짜 약 2MB CSV와 XLSX, 한글·줄바꿈·따옴표·빈값·앞자리 0, 잘못된 파일, 수식처럼 보이는 문자열, 중복 키를 검수한다.
6. 두 사용자가 같은 버전을 동시에 저장하는 경우를 검증한다. 저장 실패·연결 실패·조회 시간초과에도 기존 정상본이 바뀌지 않는지 확인한다.
7. 20개 동시 세션의 조회·편집·다운로드에서 응답·메모리·실패율을 측정한다. 목표 수치와 파일 상한은 사내 서버 성능 및 실제 행·열 수를 확인한 뒤 확정한다.
8. 의존성·외부 통신·업로드 파일·서버 권한 검수와 소스·배포 파일 대응을 기록한다. Windows·Edge와 실제 사내 서버 검증은 사내 단계에서 수행한다.
9. GitHub 전달 시 사내 에이전트용 내부 연결·운영 검수 지침과 알려진 제한을 함께 제공한다.

## 9. 사내 확인 항목과 기본 가정

요구사항 질문은 종료했다. 주요 출처는 Hue·Splunk이고, 기존 사내 계정 로그인이 있으며 부서원 모두 편집한다.

남은 환경 세부사항은 사내 에이전트의 연결 작업 항목이다. 외부 뼈대는 가짜 예시와 설정 가능한 기본값으로 개발할 수 있다. 설비 상태 분류, 새로고침 주기, 인폼의 업무별 필드, 실제 파일의 행·열 수는 사내에서 확정한다. 가짜 예시를 실제 업무 규칙으로 표현하지 않는다.

### 사내 에이전트 인계 기준
