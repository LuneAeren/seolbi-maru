# 서비스마다 API 신청이 필요한 환경

사용자 확인: 공식 API는 있으나 서비스별로 별도 신청이 필요하고, 대상 사이트 코드 수정/담당자 협조 가능 여부는 아직 모른다. 따라서 기본 방향은 **서비스별 승인을 받은 API부터 포털의 Express 연결부로 옮기는 것**이다. 브리지나 타 사이트 화면 조작을 우선하지 않는다.

## 승인과 사용자 권한을 구분한다

한 서비스의 API 승인이 다른 서비스까지 허용하지 않는다. 서비스 신청 승인, API의 허용 scope/동작, 승인 유효기간, 현재 사용자·부서·설비 권한, 사용자 위임/인증, 네트워크 연결을 각각 확인한다. API 승인이 SSO 사용자 위임이나 포털 사용자의 대상 데이터 권한까지 자동으로 해결한다는 뜻은 아니다.

미신청/심사 중/반려/만료/회수/잘못된 승인 정보는 모두 비활성으로 표시하고 실행 시에도 다시 막는다. 프런트엔드 버튼을 숨기는 것만으로 권한을 처리하지 않는다. 신청 중인 서비스를 숨긴 iframe으로 대신 호출하지 않는다.

## 이번 코드

`reference-kit/service-access.js`가 서비스별 승인 메타데이터·동작 범위·만료를 확인한다. `action-gateway.js`는 준비와 실제 실행 시 이 검사를 수행한다. 클라이언트가 `approved:true`, URL, 토큰을 보내 승인 상태를 바꿀 수 없다. 신청/승인 상태를 바꾸는 사용자용 HTTP API는 제공하지 않는다.

`demoServiceGrants()`는 가짜 설비 API=승인, 가짜 보고서 API=심사 중, 가짜 인계 API=미신청을 보여준다. 실제 신청·승인을 받았다는 표시가 아니다. `demoServiceGrants(true)`는 기존 가짜 변경 테스트용이며 회사 승인을 대신하는 옵션이 아니다. production 디스패치는 기존대로 차단한다.

사내 이식 시 승인 담당자/신뢰된 서버 프로세스가 제공한 정보를 읽는다. 현재 키트는 실제 신청 시스템과 동기화하지 않는다. 정보 수집 실패/허용 기간 만료 시 기본 차단하고, 원천 API도 사용자와 scope를 자체 검증해야 한다. 실제 제공자 scope는 예제의 논리 action ID와 명시적으로 매핑한다.

## 사내에서 채울 신청 양식

| 항목 | 작성 내용 |
| --- | --- |
| 서비스/담당자 | 사내에서만 보관할 이름과 담당 조직 |
| 신청 목적 | 예: 부서 포털에서 설비 현황 조회, 첫 단계는 읽기 전용 |
| 소비 주체 | 포털 애플리케이션·사용자/부서 범위 |
| 필요한 API/권한 | 승인받을 endpoint·method·scope·리소스, 최소 범위 |
| 인증/사용자 위임 | 제공자가 지원하는 방식과 서비스별 차이 |
| 테스트/운영 구분 | 각각의 신청/계정/허용 범위 |
| 응답 계약 | 필요한 필드·단위·갱신 시각·오류·로그인 만료 |
| 제한 | 호출량·동시 실행·응답 크기·timeout·캐시 허용 여부 |
| 변경 기능 | 원천 업무 키·멱등 키·실행 결과 조회·대사 방법 |
| 유효기간/회수 | 승인 만료·갱신·변경 통지·회수 반영 방식 |
| 네트워크 | 승인된 내부 목적지·포트·TLS·서버 egress |

신청 ID·실제 주소·사용자·키·토큰은 이 GitHub 저장소에 적지 않는다. 아직 API별로 상세 사양을 모르는 상태이므로 특정 인증/호출 규약을 임의로 만들지 않는다. 첫 번째 승인된 조회 API 한 개로 권한·오류·세션 만료·리소스를 검증한 후 같은 구조를 다른 서비스에 반복한다.
